# WhatHome

A self-hosted home device inventory application. Track devices across one or more homes, organized by floor and room, with search and filtering. See `SPEC.md` for the full product specification.

## ⚠️ Security warning

**This application has no authentication or authorization.** Anyone who can reach it on the network can view, create, edit, and delete all data. It is designed for use on a trusted home network only.

**Do not expose this application to the public internet.** Do not port-forward it, do not put it behind a public reverse proxy without adding your own authentication layer, and do not deploy it to a publicly reachable host.

## Requirements

- Docker and Docker Compose (for the standard deployment)
- Node.js 22+ and npm (for local development without Docker)

## Running with Docker Compose

1. Copy the example environment file and adjust values as needed:

   ```bash
   cp .env.example .env
   ```

2. Start the stack:

   ```bash
   docker compose up -d
   ```

   This builds the application image, starts PostgreSQL with a persistent named volume, applies any pending database migrations, and starts the web application once migrations succeed. Both services have health checks; `docker compose ps` shows `healthy` once ready.

3. Open `http://localhost:3000` (or the port set in `APP_PORT`).

Data persists in the `whathome-postgres-data` named volume across `docker compose restart`, `docker compose down` / `up`, and container recreation. It is only lost if the named volume itself is explicitly deleted (`docker compose down -v` or `docker volume rm`).

## Local development (without Docker for the app)

1. Start a local PostgreSQL instance (Docker is one option):

   ```bash
   docker run -d --name whathome-dev-postgres \
     -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=whathome \
     -p 5432:5432 postgres:17-alpine
   ```

2. Copy `.env.example` to `.env` and set `DATABASE_URL` to point at that database, e.g.:

   ```
   DATABASE_URL=postgres://postgres:postgres@localhost:5432/whathome
   ```

3. Install dependencies and apply migrations:

   ```bash
   npm install
   npm run db:migrate
   ```

4. Start the dev server:

   ```bash
   npm run dev
   ```

## Database migrations

Migrations are committed SQL files generated by Drizzle Kit and live in `drizzle/`.

- `npm run db:generate` — generate a new migration from schema changes in `server/db/schema.ts`.
- `npm run db:migrate` — apply pending migrations to the database at `DATABASE_URL`.
- `npm run db:studio` — open Drizzle Studio against the configured database.

The Docker image applies pending migrations automatically on container start, before the application begins accepting traffic. A failed migration stops the container from starting.

## Project structure

See `SPEC.md` section 13 for the intended layout. In short:

- `app/` — Vue pages, components, composables, layouts (Nuxt 4 `srcDir`).
- `server/` — Nitro API routes, database schema/client, repositories, services, utilities.
- `shared/` — Zod validation schemas and TypeScript types used by both client and server.
- `drizzle/` — committed SQL migrations.
- `tests/` — unit, integration, and end-to-end tests.

Business rules live in `server/services/*`, not in API route handlers or Vue components. Route handlers parse input, call a service, and format the response; components call the API composables in `app/composables/*`.
