# Home Device Inventory Application Specification

## 1. Summary

Build a self-hosted web application for recording devices across one or more homes.

Each home can contain floors, each floor can contain rooms, and each home can contain devices. A device always belongs to one home and may optionally be assigned to a room or marked as being in storage.

The application will run through Docker Compose, be usable from multiple devices on the home network, and retain its data in a PostgreSQL database.

No authentication is required.

## 2. Goals

The first version must allow the user to:

1. Create, view, edit, and delete homes.
2. Create, view, edit, reorder, and delete floors within a home.
3. Create, view, edit, and delete rooms within a floor.
4. Create, view, edit, and delete devices within a home.
5. place each device in exactly one location state:
   - Unassigned
   - In Storage
   - In Room
6. Search and filter the device inventory.
7. Use the application from desktop and mobile browsers.
8. Retain data across application and container restarts.

## 3. Out of Scope

The first version will not include:

- User accounts or authentication.
- User roles or permissions.
- Home Assistant integration.
- Automatic device discovery.
- Device control or automation.
- Live device availability checks.
- Network scanning.
- Import or export.
- Backup management beyond the persistent database volume.
- Internet-facing deployment support.
- Native mobile applications.

Home Assistant integration may be added later. The data model and service boundaries must not prevent a future import feature.

## 4. Technology

The application will use:

- Nuxt 4 as the full-stack Vue framework.
- Vue 3 Composition API and single-file components.
- TypeScript in strict mode.
- Nuxt server routes for the HTTP API.
- PostgreSQL for persistent storage.
- Drizzle ORM and committed SQL migrations.
- A schema-validation library shared by forms and server endpoints.
- Docker Compose for local deployment.
- A responsive Vue component system.
- Vitest for unit and service tests.
- Playwright for browser-level tests.
- ESLint, formatting, type checking, and automated dependency updates.

The project will be a single full-stack codebase. The browser interface and server API will be deployed together, with PostgreSQL running as a separate Docker Compose service.

Package versions will be pinned in the lockfile. Experimental libraries must be isolated behind local interfaces so they can be replaced without changing the domain model.

- [Vue application guidance](https://vuejs.org/guide/introduction.html)
- [Nuxt server framework](https://nuxt.com/docs/4.x/getting-started/server)
- [Drizzle PostgreSQL support](https://orm.drizzle.team/docs/get-started/postgresql-new)

## 5. Domain Model

```text
Home
 ├── Floor
 │    └── Room
 └── Device
      └── optional Room relationship
```

### 5.1 Home

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Generated by the server |
| `name` | String | Required, trimmed, 1–120 characters |
| `createdAt` | Timestamp | Generated by the server |
| `updatedAt` | Timestamp | Updated on every change |
| `version` | Integer | Used to prevent conflicting edits |

A home owns all its floors, rooms, and devices.

### 5.2 Floor

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Generated by the server |
| `homeId` | UUID | Required home relationship |
| `name` | String | Required, trimmed, 1–120 characters |
| `position` | Integer | Controls display order |
| `createdAt` | Timestamp | Generated by the server |
| `updatedAt` | Timestamp | Updated on every change |
| `version` | Integer | Used to prevent conflicting edits |

Floor names must be unique within the same home, ignoring letter case.

Examples include Basement, Ground Floor, First Floor, Upstairs, and Outside.

### 5.3 Room

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Generated by the server |
| `floorId` | UUID | Required floor relationship |
| `homeId` | UUID | Must match the floor’s home |
| `name` | String | Required, trimmed, 1–120 characters |
| `position` | Integer | Controls display order |
| `createdAt` | Timestamp | Generated by the server |
| `updatedAt` | Timestamp | Updated on every change |
| `version` | Integer | Used to prevent conflicting edits |

Room names must be unique within the same floor, ignoring letter case.

### 5.4 Device

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Generated by the server |
| `homeId` | UUID | Required |
| `roomId` | UUID or null | Optional; room must belong to the same home |
| `inStorage` | Boolean | Defaults to `false` |
| `name` | String | Required, trimmed, 1–160 characters |
| `type` | String | Required, trimmed, 1–80 characters |
| `protocol` | String | Required, trimmed, 1–80 characters |
| `manufacturer` | String or null | Optional, maximum 120 characters |
| `model` | String or null | Optional, maximum 120 characters |
| `serialNumber` | String or null | Optional, maximum 160 characters |
| `ipAddress` | IPv4, IPv6, or null | Optional and validated |
| `notes` | String or null | Optional, maximum 5,000 characters |
| `purchaseDate` | Date or null | Optional date without a time |
| `createdAt` | Timestamp | Generated by the server |
| `updatedAt` | Timestamp | Updated on every change |
| `version` | Integer | Used to prevent conflicting edits |

Serial numbers and IP addresses are not required to be unique.

## 6. Device Location Rules

Every device must resolve to exactly one location state.

| State | `roomId` | `inStorage` |
|---|---:|---:|
| Unassigned | null | false |
| In Storage | null | true |
| In Room | populated | false |

The following state is invalid and must be rejected:

```text
roomId is populated AND inStorage is true
```

The interface presents these states as a single-choice control rather than independent checkboxes.

When `In Room` is selected:

- A room becomes required.
- Only rooms belonging to the device’s home may be selected.
- Rooms are grouped by floor in the selector.

When a room is deleted:

- Its devices are not deleted.
- Their `roomId` becomes null.
- Their location becomes `Unassigned`.

When a floor is deleted:

- All rooms on that floor are deleted.
- Devices assigned to those rooms remain in the home.
- Those devices become `Unassigned`.

## 7. Deletion Rules

### Delete a room

The application must display the number of affected devices before confirmation.

After confirmation:

1. Unlink affected devices.
2. Delete the room.
3. Keep affected devices as `Unassigned`.

### Delete a floor

The application must display:

- The number of rooms being deleted.
- The number of devices that will become unassigned.

After confirmation:

1. Unlink affected devices.
2. Delete the floor and its rooms.
3. Keep affected devices as `Unassigned`.

### Delete a home

The application must display the number of floors, rooms, and devices that will be permanently deleted.

The user must confirm the deletion using the home’s name. After confirmation, the home and all related records are permanently deleted in one database transaction.

## 8. User Interface

### 8.1 Homes page

The initial page displays all homes.

The user can:

- Create a home.
- Open a home.
- Rename a home.
- Delete a home.
- See counts for floors, rooms, and devices.

An empty state explains how to create the first home.

### 8.2 Home overview

The home overview displays:

- Total device count.
- Devices in rooms.
- Devices in storage.
- Unassigned devices.
- Floor and room hierarchy.
- Recent inventory changes.
- Actions to add a floor, room, or device.

### 8.3 Floors and rooms

Floors appear in their configured order. Rooms appear under their floor.

The user can:

- Add, rename, reorder, and delete floors.
- Add, rename, reorder, and delete rooms.
- View the devices assigned to a room.
- See how many devices will be affected before deleting a floor or room.

A room can be created only after its home has at least one floor.

### 8.4 Device inventory

Desktop layouts use a sortable table. Narrow screens use device cards.

Each result displays:

- Name
- Type
- Protocol
- Manufacturer and model
- Location
- IP address
- Purchase date

The inventory supports:

- Partial text search across name, manufacturer, model, serial number, IP address, type, and protocol.
- Filtering by home.
- Filtering by floor.
- Filtering by room.
- Filtering by location state.
- Filtering by type.
- Filtering by protocol.
- Filtering by manufacturer.
- Sorting by name, purchase date, manufacturer, type, and most recently updated.
- A clear-all-filters action.
- A useful empty state when no devices match.

### 8.5 Device form

The form contains:

1. Name
2. Type
3. Protocol
4. Manufacturer
5. Model
6. Serial number
7. IP address
8. Purchase date
9. Location state
10. Room, when `In Room` is selected
11. Notes

Type and protocol inputs offer suggestions based on values already used in the inventory while still accepting new free-text values.

Validation errors appear next to the relevant fields and do not erase entered data.

### 8.6 Device details

The details view displays every recorded field, its current location, and created/updated timestamps.

The user can:

- Edit the device.
- Change its location.
- Delete the device.
- Return to the previous filtered inventory view.

### 8.7 Responsive and accessible behaviour

The interface must:

- Work at widths from 360 pixels upward.
- Support keyboard navigation.
- Use visible focus indicators.
- Associate labels and errors with form controls.
- Avoid relying on colour alone to communicate state.
- Meet WCAG 2.2 AA colour contrast requirements.
- Ask for confirmation before destructive operations.

## 9. API

All endpoints use JSON and are served under `/api`.

### Homes

```text
GET    /api/homes
POST   /api/homes
GET    /api/homes/:homeId
PATCH  /api/homes/:homeId
DELETE /api/homes/:homeId
```

### Floors

```text
GET    /api/homes/:homeId/floors
POST   /api/homes/:homeId/floors
PATCH  /api/floors/:floorId
DELETE /api/floors/:floorId
POST   /api/homes/:homeId/floors/reorder
```

### Rooms

```text
GET    /api/homes/:homeId/rooms
POST   /api/floors/:floorId/rooms
PATCH  /api/rooms/:roomId
DELETE /api/rooms/:roomId
POST   /api/floors/:floorId/rooms/reorder
```

### Devices

```text
GET    /api/homes/:homeId/devices
POST   /api/homes/:homeId/devices
GET    /api/devices/:deviceId
PATCH  /api/devices/:deviceId
DELETE /api/devices/:deviceId
```

The device list endpoint accepts search, filter, sort, page, and page-size parameters.

### Suggestions

```text
GET /api/homes/:homeId/device-suggestions/types
GET /api/homes/:homeId/device-suggestions/protocols
GET /api/homes/:homeId/device-suggestions/manufacturers
```

Suggestions are calculated from existing device values. Separate type and protocol management screens are not required.

### Success response

```json
{
  "data": {}
}
```

### List response

```json
{
  "data": [],
  "page": {
    "number": 1,
    "size": 25,
    "totalItems": 0,
    "totalPages": 0
  }
}
```

### Error response

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The submitted data is invalid.",
    "fieldErrors": {
      "ipAddress": ["Enter a valid IPv4 or IPv6 address."]
    },
    "requestId": "generated-request-id"
  }
}
```

Expected status codes include:

- `200` for successful reads and updates.
- `201` for successful creation.
- `204` for successful deletion.
- `400` for malformed requests.
- `404` for missing resources.
- `409` for duplicate names or conflicting edits.
- `422` for field validation failures.
- `500` for unexpected server failures.

## 10. Concurrent Editing

Because multiple devices can access the inventory, update and delete requests include the record’s current `version`.

If another browser has changed the record since it was loaded:

- The server returns `409 Conflict`.
- The application keeps the user’s entered data.
- The application explains that the record changed elsewhere.
- The user can reload the current version before retrying.

## 11. Persistence and Docker

Docker Compose will define:

1. An application service.
2. A PostgreSQL service.
3. A named volume for PostgreSQL data.

The deployment must:

- Start with `docker compose up -d`.
- Persist data when either container restarts or is recreated.
- Apply pending database migrations before the application accepts traffic.
- Include health checks for the application and database.
- Restart services automatically unless explicitly stopped.
- Read configuration from environment variables.
- Avoid embedding passwords or environment-specific values in images.
- Provide an `.env.example` containing safe example values.

No claim is made that data will survive deliberate deletion of the Docker volume.

Because authentication is intentionally absent, the documentation must warn against exposing the application directly to the public internet.

## 12. Failure Handling

- Database operations that affect multiple records must use transactions.
- Failed deletes must leave all affected records unchanged.
- Forms must preserve entered values after server errors.
- Loading and saving states must be visible.
- Repeated submissions must not create duplicate records.
- Invalid or cross-home room assignments must be rejected.
- A failed migration must prevent application startup and produce a readable error.
- Unexpected server errors must return a request identifier without exposing stack traces to the browser.

## 14. Testing Plan

### Unit tests

Cover:

- Device location-state validation.
- Required and optional device fields.
- IPv4 and IPv6 validation.
- Home, floor, and room name validation.
- Search and filter parameter parsing.
- Version-conflict handling.

Minimum: 15 focused unit tests.

### Integration tests

Use a real temporary PostgreSQL database to cover:

- Home, floor, room, and device CRUD.
- Room assignment restricted to the same home.
- Room deletion unlinking devices.
- Floor deletion unlinking devices.
- Home deletion removing all descendants.
- Transaction rollback after a simulated failure.
- Duplicate floor and room names.
- Concurrent update conflicts.
- Data remaining after application restart.

Minimum: 15 integration tests.

### End-to-end tests

Cover these browser journeys:

1. Create a home, floor, room, and room-assigned device.
2. Create a device in storage.
3. Create an unassigned device.
4. Move a device between all three location states.
5. Delete a room and verify that its devices become unassigned.
6. Search and filter the device inventory.
7. Edit a device from a mobile-sized viewport.
8. Delete a home using the required confirmation.

Minimum: 8 end-to-end scenarios.

## 15. Acceptance Criteria

1. A user can create, rename, view, and delete multiple homes.
2. A user can create, rename, reorder, view, and delete floors within a home.
3. A user can create, rename, reorder, view, and delete rooms within a floor.
4. A user can create a device using only name, type, and protocol.
5. All optional device fields can be stored, edited, cleared, and displayed.
6. Every device belongs to exactly one home.
7. Every device is unassigned, in storage, or assigned to one room.
8. A device cannot be both in storage and assigned to a room.
9. A device cannot reference a room from another home.
10. Deleting a room preserves its devices and makes them unassigned.
11. Deleting a floor deletes its rooms but preserves affected devices as unassigned.
12. Deleting a home permanently deletes its floors, rooms, and devices after typed confirmation.
13. Device search is case-insensitive and searches all specified fields.
14. All specified device filters can be combined and cleared.
15. Data remains available after application and database containers restart.
16. Conflicting edits from two browsers do not silently overwrite one another.
17. The application is usable at a viewport width of 360 pixels.
18. All forms provide accessible labels and visible validation errors.
19. `docker compose up -d` starts a healthy application from a clean checkout.
20. Unit, integration, and end-to-end test suites pass.
21. Type checking, linting, and production builds pass.
22. The documentation warns that the unauthenticated application must not be publicly exposed.

## 16. Rollback Plan

Application changes are rolled back by redeploying the previous application image.

Database changes require forward and reverse migration instructions where reversal does not risk data loss. A migration that removes or transforms data must document a backup step before it is applied.

The PostgreSQL named volume must not be removed during a normal application rollback.

## 18. Future Compatibility

A future Home Assistant integration should be implemented as a separate import adapter.

To prepare for that work without expanding the MVP:

- Device persistence remains behind a service layer.
- Internally generated UUIDs remain the application’s primary identifiers.
- Future external source identifiers can be added without changing existing IDs.
- Type and protocol values remain extensible.
- Import logic will not be embedded in Vue components or core database queries.
