# WhatHome

A self-hosted home device inventory application. Track devices across one or more homes, organized by floor and room, with search, filtering, and CSV import.

Devices can be bulk-created from a CSV file on the inventory page ("Import CSV"). The dialog shows the required and optional columns, offers a template download, and matches headers flexibly (case/spacing-insensitive, with common aliases like "Brand" for Manufacturer). Each row is validated independently, so a file with some invalid rows still imports the valid ones and reports exactly what's wrong with the rest.

## ⚠️ Security warning

**This application has no authentication or authorization.** Anyone who can reach it on the network can view, create, edit, and delete all data. It is designed for use on a trusted home network only.

**Do not expose this application to the public internet without adding your own authentication layer.** Do not port-forward it, do not put it behind a public reverse proxy without authentication, and if you deploy it to a publicly reachable host (including Vercel — see below), put it behind that platform's access controls (e.g. [Vercel Deployment Protection](https://vercel.com/docs/deployment-protection)) or your own auth middleware first.

## Requirements

- Docker and Docker Compose (for the standard deployment)
- Node.js 22+ and npm (for local development without Docker)

## Running with Docker Compose

1. Copy the example environment file and adjust values as needed:

   ```bash
   cp .env.example .env
   ```

2. Start the stack:

   ```bash
   docker compose up -d
   ```

   This builds the application image, starts PostgreSQL with a persistent named volume, applies any pending database migrations, and starts the web application once migrations succeed. Both services have health checks; `docker compose ps` shows `healthy` once ready.

3. Open `http://localhost:3000` (or the port set in `APP_PORT`).

Data persists in the `whathome-postgres-data` named volume across `docker compose restart`, `docker compose down` / `up`, and container recreation. It is only lost if the named volume itself is explicitly deleted (`docker compose down -v` or `docker volume rm`).

## Deploying to Vercel with Neon

The app deploys to Vercel as-is (Nuxt's Nitro server auto-detects the Vercel build environment, no extra config needed). To back it with [Neon](https://neon.tech) serverless Postgres:

1. In your Vercel project, add a Neon database — either through the [Neon Vercel integration](https://vercel.com/marketplace/neon) or Vercel's native Postgres storage (which is also Neon-backed) — or create a Neon project yourself and copy its connection string.
2. Set the `DATABASE_URL` environment variable on the Vercel project to that Neon connection string (it should contain `neon.tech` in the hostname).
3. Deploy. The `vercel-build` script (`tsx server/db/migrate.ts && nuxt build`) runs pending migrations against `DATABASE_URL` as part of every build, before the new deployment starts serving traffic — mirroring what the Docker entrypoint does for self-hosted deployments.

The database driver is chosen automatically at runtime based on `DATABASE_URL`: a `neon.tech` hostname uses Neon's WebSocket driver (`drizzle-orm/neon-serverless`), which is safe to use per-request in a serverless function and still supports real, interactive `db.transaction()` calls, exactly like the plain `postgres-js` driver used against a self-hosted Postgres. No code changes are needed to switch between the two — only `DATABASE_URL`.

This requires the Node.js 22 runtime (set via the `engines` field in `package.json`, which Vercel reads automatically) for the Neon driver's WebSocket support.

Remember the security warning above: a Vercel deployment is publicly reachable by default, and this app has no authentication of its own.

## Local development (without Docker for the app)

1. Start a local PostgreSQL instance (Docker is one option):

   ```bash
   docker run -d --name whathome-dev-postgres \
     -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=whathome \
     -p 5432:5432 postgres:17-alpine
   ```

2. Copy `.env.example` to `.env` and set `DATABASE_URL` to point at that database, e.g.:

   ```
   DATABASE_URL=postgres://postgres:postgres@localhost:5432/whathome
   ```

3. Install dependencies and apply migrations:

   ```bash
   npm install
   npm run db:migrate
   ```

4. Start the dev server:

   ```bash
   npm run dev
   ```

## Database migrations

Migrations are committed SQL files generated by Drizzle Kit and live in `drizzle/`.

- `npm run db:generate` — generate a new migration from schema changes in `server/db/schema.ts`.
- `npm run db:migrate` — apply pending migrations to the database at `DATABASE_URL`.
- `npm run db:studio` — open Drizzle Studio against the configured database.

The Docker image applies pending migrations automatically on container start, before the application begins accepting traffic. A failed migration stops the container from starting. On Vercel, the `vercel-build` script applies migrations during the build step instead, before the deployment goes live.

## Project structure

The main source areas are:

- `app/` — Vue pages, components, composables, layouts (Nuxt 4 `srcDir`).
- `server/` — Nitro API routes, database schema/client, repositories, services, utilities.
- `shared/` — Zod validation schemas and TypeScript types used by both client and server.
- `drizzle/` — committed SQL migrations.
- `tests/` — unit, integration, and end-to-end tests.

Business rules live in `server/services/*`, not in API route handlers or Vue components. Route handlers parse input, call a service, and format the response; components call the API composables in `app/composables/*`.
